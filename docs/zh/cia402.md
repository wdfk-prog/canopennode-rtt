# CiA 402 Device 交付、诊断与互操作

本文定义 A7 的产品化集成契约，用于把现有多轴 Device 实现推进到可交付 profile。PDS、operation mode 和同步实时路径仍分别以 [Pure-C Device Core](cia402-device-core.md) 与 [RT-Thread Device Thread](cia402-device-rtt.md) 为准；A7 不重写这些既有契约。

![CiA 402 EMCY 诊断流](../assets/cia402-emcy-diagnostic-flow.svg)

## 诊断模型

每个 logical device 独立维护 fault latch，并对应标准 Error code 对象 `0x603F`、`0x683F` 或 `0x703F`。产品通过 `CO_402_device_diag_if_t` 提供故障映射，核心层不擅自发明产品错误分类。映射中的 PDS Error code、CANopen EMCY code 和 manufacturer information 是三个独立字段。

启用 `PKG_CANOPENNODE_CIA402_DEVICE_DIAGNOSTICS` 后，Pure-C Device 层在首次故障时锁存该 axis，更新对应 Error code，并生成 pending diagnostic event；同一个已锁存故障在 supervisor 重复处理时不会重复上报。只有现有 CiA 402 Fault Reset transaction 成功后，才清除该 axis 的 Error code 并生成 reset event，不影响其他轴。

RT-Thread EMCY 桥由 `PKG_CANOPENNODE_CIA402_DEVICE_RTT_EMCY_BRIDGE` 控制。Axis source 使用 CANopenNode manufacturer-specific error-bit 区间，编码为 `0x40 + logicalDevice`，因此 Axis0/1/2 分别为 `0x40/0x41/0x42`。桥接层只在 OD lock 已释放、但 lifecycle mutex 仍保护当前 `CO_t` 时调用 `CO_errorReport()` / `CO_errorReset()`，不会把 EMCY mutex、日志或阻塞路径塞进 `co_rt` 的 SYNC/RPDO/TPDO fast path。

Communication Reset 会重新绑定 generated OD，恢复每个 active fault 对应的 Error code，并把 active diagnosis 安排到新的 `CO_EM_t` 上 replay；该过程不重新执行 DriveIF power transition。CAN bus-off 属于 CANopen communication fault，不得被错误编码成某个 axis fault。

## 产品描述与发布 artifact

`examples/demo_device` 继续作为 bring-up/test data model，可以包含 manufacturer test object。产品式集成使用 `examples/cia402_multi_axis_device` 作为发布 staging contract，并关闭 `PKG_CANOPENNODE_USING_DEMO_OD`；实际 BSP/Application 编译由所选产品 XDD 同源生成的 `OD.c/OD.h`。

发布集合必须来自同一冻结 revision：

```text
project.xdd -> OD.c / OD.h / project.eds / project.md
                 + manifest.json
```

`manifest.json` 记录 XDD description version、CANopenEditor 版本、source revision、选定 normative baseline、`0x1018` identity，以及每个 generated artifact 的 SHA-256。静态检查命令：

```sh
python3 .github/ci/canopennode-rtt/verify-cia402-artifacts.py examples/cia402_multi_axis_device
```

检查器会验证 hash、description version、`0x1018` identity、三轴 release object matrix、`0x603F/0x683F/0x703F` 属性，并拒绝包含 test-only `0x2300..0x23FF` 的产品 artifact。它不能证明 CI 中重新执行了 CANopenEditor，也不能证明目标固件实际运行的就是这份 OD。

## Build/Test profile

`demo-cia402-device-rtt-autostart` 保留为 A6 兼容 profile，A7 diagnostics 关闭；`demo-cia402-a7-validation` 在原三轴、mode、SYNC demo 配置上启用 per-axis diagnostics 与 deferred EMCY bridge，用于覆盖 diagnostics on/off 的 source-selection 与回滚边界。

真正的 product-reference build 还必须关闭 package demo OD，并由 BSP/Application 加入产品 generated OD。产品 identity、normative baseline 和 source revision 尚未冻结时，仓库不应伪造一套看似“可发布”的 generated artifact。

## 互操作验收

![CiA 402 产品验证拓扑](../assets/cia402-product-validation-topology.svg)

配套 Linux Host 测试应以发布 EDS 为输入，通过标准 identity/profile 信息发现设备。Manufacturer object 可以作为确定性 fault injection 的测试入口，但设备识别、正常 SDO/PDO/PDS 控制和主站导入不得依赖私有 magic index。

A7 closing evidence 至少覆盖 Axis0/1/2 SDO、PDO、独立 PDS、mixed mode、one-axis fault 与 EMCY source、NMT reset/rebind、CSP/CSV/CST SYNC、bus-off/recovery，以及长期 reset/fault stress。Host unit 和 CI static check 只能证明各自层级，不能替代目标板 CAN、真实主站/analyzer import 或 HIL 时序与恢复证据。

只有发布 XDD/EDS 与运行固件 OD 一致，并且至少一个目标主站能直接导入并运行设备、不依赖项目私有识别 workaround 后，才应把 Device Milestone A 标记为完成；当前证据也不应扩大为 CiA 402 conformity/certification 声明。
